## Why this layer exists, precisely

`@flybyme/mesh-ui` (an earlier UI framework by the same author) has a `Signal.ts` and a
`BaseComponent.ts`, and the component class does not use the signal. The result is this, and it is
the specific defect this whole package replaces:

```ts
public updateProps(newProps: Partial<TProps>): void {
    this._props = { ...this._props, ...newProps };
    this.element.innerHTML = '';   // discards the entire subtree
    this.render();                 // rebuilds it from scratch
}
```

Every prop change destroys and rebuilds everything below it: focus lost mid-typing, scroll reset,
child state gone. For a console streaming live data into many panels that is the difference between
usable and not.

Reactivity is specified and built **before** components specifically so the component layer never
has that escape hatch available. Your job is to make a subtree rebuild structurally unnecessary.

## Scope: this dispatch builds ONLY the reactive core

Build in `src/runtime/reactivity/`. Do not build components, `h()`, DOM, routing, the compositor,
or anything that touches a browser API. This layer is pure state propagation and must be testable
in plain node with no DOM.

### 1. `signal`, `computed`, `effect`

```ts
const count = signal(0);
count();                                        // read  -> 0
count.set(1);                                   // write
count.update(n => n + 1);                       // write from previous

const doubled = computed(() => count() * 2);    // derived, cached, read-only
effect(() => console.log(count()));             // runs now, re-runs on change
```

Required properties, each of which needs a test that would genuinely fail if it regressed:

- **Automatic dependency tracking.** Reading a signal inside a `computed`/`effect` subscribes to it.
  No dependency arrays.
- **Dynamic dependencies.** If an effect reads `a()` then, after a branch flips, reads `b()` and no
  longer `a()`, it must stop re-running when `a` changes. Stale subscriptions are a leak and a
  correctness bug, not an inefficiency.
- **Fine-grained.** An effect re-runs only when something it *actually read* changed. Writing a
  signal to the value it already holds notifies nobody (compare with `Object.is`).
- **Glitch-free.** A `computed` never observes an inconsistent intermediate state. The classic
  diamond — `a` -> `b`, `a` -> `c`, `b`+`c` -> `d` — must run `d` exactly once per change to `a`,
  and never with a mixed old/new pair. Test the diamond explicitly; it is where naive
  implementations fail.
- **Batched.** Synchronous writes in one tick coalesce into one flush. Writing three signals runs a
  dependent effect once, not three times. Provide `batch(fn)` for explicit grouping.
- **Lazy computeds.** A `computed` nobody reads does not evaluate. Recomputation happens on read
  after invalidation, not eagerly on write.
- **Disposal.** `effect()` returns a dispose function. Disposing unsubscribes from everything,
  including dependencies picked up on the most recent run.
- **`computed` must be pure.** Writing to a signal inside a `computed` throws in development. So
  does a cycle (a computed that reads itself, directly or transitively) — with a message that names
  the cycle rather than blowing the stack.

Nested effects: an inner effect created inside an outer effect's body is disposed when the outer
re-runs, or it leaks one more inner effect on every single run. Get this right and test it.

### 2. `resource`

```ts
const cards = resource(() => api.kanban.board_list({ repo: repo() }));
cards.loading();   // Signal<boolean>
cards.error();     // Signal<Error | null>
cards.data();      // Signal<T | undefined>
cards.refetch();
```

- Re-fetches when a signal read inside the fetcher changes — same tracking as `computed`.
- **Out-of-order responses must not clobber.** If input changes from A to B and A's response lands
  after B's, A's result is discarded. This is the bug every hand-rolled data hook has; it must be
  impossible here. Test it with deliberately inverted resolution order.
- In-flight dedupe for identical concurrent requests.
- An error populates `error()` and leaves the last good `data()` intact rather than blanking the UI.
- `resource` takes the fetcher only. It knows nothing about HTTP, mesh, or the generated client —
  those arrive as a closure. Keep this layer dependency-free.

### 3. `ReactiveScope` — how the runtime disposes things

Apps do not track their own subscriptions (spec/05: "No manual subscription bookkeeping in app
code"). Provide a scope object that owns everything created inside it and tears it all down at
once. `ctx.state` in later phases will be built on this; build the mechanism, not `ctx`.

  const scope = createScope();
  scope.run(() => { /* effects and resources created here belong to the scope */ });
  scope.dispose();   // every effect disposed, every resource cancelled, idempotent

Disposing a scope twice must be safe, and an effect that throws during disposal must not prevent
the remaining ones from being disposed.

## Rules

- **Do not `git commit`.** Leave the work in the working tree.
- **Zero `as any`, `as unknown as`, `as never`.** Absolute here, and not stylistic: `mesh-ui`'s
  `getChildren()` returning `element.children` cast to `BaseComponent[]` is a real runtime bug
  caused by exactly this. Generics over an internal graph will tempt you — resist, and if you
  genuinely cannot type something, say so in your summary instead of casting.
- **No dependencies.** Not zod, not mesh, nothing. This is a self-contained module. It must be
  importable in a browser bundle with no transitive weight.
- `npm run typecheck` (which covers `src` AND `test` — use it, plain `tsc` skips the tests) and
  `npx vitest run` must both pass clean.
- Comments explain *why*, not *what*. The house style is in `src/exposure/broker.ts`,
  `src/exposure/input.ts`, and `src/auth/session.ts` — read one before you start writing.
- Do NOT touch anything outside `src/runtime/reactivity/`, `test/reactivity*.test.ts`, and the one
  export block you add to `src/index.ts`. Another dispatch may be running elsewhere.
- Do not build: components, `h()`, DOM helpers, `When`/`For`, routing, the compositor, the
  manifest, or SSE. Later phases.

## A warning specific to this task

Reactive systems are easy to write so that they pass hand-written tests and are still wrong: the
diamond runs twice, a dynamic dependency never unsubscribes, a nested effect leaks one instance per
run. Write the adversarial tests **first** and make them fail before you make them pass. If any of
the listed properties is one you could not actually get right, say so plainly — a known gap is far
cheaper than a silent one in the substrate that everything else is built on.
