## Why this app, and why it matters more than it looks

Five phases of framework exist with ~190 passing tests, and **nothing has ever used it**. Every
real defect found in this package so far came from a consumer running it — an MCP transport that
500s on the second request, a `.css` import that crashes Node at startup, a base path that 404s
against its own server. None were caught by tests.

So the deliverable is two things: a working app, **and an honest report of everything the framework
made hard.** The second is worth more. Do not work around framework problems silently — record them.

## What it manages

The `domain` collection (`/home/ubuntu/code/paas/src/tenancy/tenancy.schema.ts`, `DomainSchema`):

```ts
orgId              // -> organization, or the sentinel 'platform'
fqdn               // e.g. example.com
registrar?         // enum
verificationStatus // enum, written by domain_verify
dnsZoneId?         // -> dnsZone
status             // enum, default 'active'
```

Plain `defineCrud('domain', ...)`, so `domain.find`, `domain.resolve`, `domain.create`,
`domain.update`, `domain.delete` all exist.

Related, for the detail view: `dns.record_create`, `dns.propagation_check`, and `dnsRecord.find`.

## Build

**`apps/domains.ts`** — one app, `defineApp`, with two views under a single `page` surface routed
at `/domains/*`:

- **List.** A `Table` of domains (from `Form`/`Table` generation, dispatch #8 — read
  `src/runtime/dom/` for what actually exists rather than assuming a shape). Filter by `fqdn` via a
  signal. Each row links to the detail view with a real `<a href>`, so middle-click and
  open-in-new-tab work — `spec/06` calls that out specifically.
- **Detail.** One domain, its DNS records, and its verification status. A `Form` generated from
  `domain.create`'s contract for adding one.

**A manifest** (`manifest.yaml`) declaring the app, per `spec/09`.

Data through `resource` (`spec/08`), not hand-rolled fetch. Per-app state through `ctx.state` so it
is disposed on unload.

## Constraints that are the point of the exercise

- **The app never places itself.** It requests a `page` surface and the compositor decides. If a
  surface request is refused, handle it — refusal is a normal outcome, not an error.
- **Real `<a href>` for navigation**, not click handlers that call the router. Middle-click, copy
  link address, and open-in-new-tab must work without anyone implementing them.
- **No `as any` / `as unknown as` / `as never`.** Absolute in this codebase.
- Keyed `For`/`Table` everywhere a list renders, so filtering and sorting move nodes rather than
  rebuilding them — that is the property the whole framework exists for.

## Rules

- **Do not `git commit`.** Leave the work in the working tree.
- No new dependencies.
- **DOM test files need `// @vitest-environment happy-dom` at the top.** Vitest 4 removed
  `environmentMatchGlobs`; without the docblock a file silently has no `document`.
- **Effects are microtask-scheduled** — a write followed immediately by a DOM assertion tests the
  scheduler, not your code. Use `flushSync()`.
- `npm run typecheck` and `npx vitest run` must pass with all existing tests green.
- Do not modify `src/runtime/dom/` or `src/runtime/app/` to make your app easier. If the framework
  is missing something, **write it in your summary** — that finding is the point. Only fix a
  framework bug if it makes the app impossible, and say so loudly if you do.
