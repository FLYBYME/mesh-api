## What to build

### 1. `src/runtime/router/` — the router

**Real URLs, History API only. No hash routing.** Per spec/07.

- Three levels, in order: **namespace → app → view**. A path resolves to which namespace an app
  came from, which app owns the subtree, and which view within that app.
- Route params and the query string are exposed as **signals**, so a view reading `params.id()`
  re-renders on navigation without re-mounting.
- Real `<a href>` navigation is intercepted for same-origin links only — middle-click,
  cmd/ctrl-click, `target="_blank"`, and modified clicks must fall through to the browser. Getting
  this wrong breaks open-in-new-tab, which spec/06 calls out as a thing that must work without
  anyone implementing it.
- Scroll and focus restoration across back/forward.
- **Namespace prefixes** (`12-network-and-federation.md`): a remote app mounts under a prefix
  (`/b/shop/product/xyz`) and **must not know it is prefixed** — it routes within its own subtree
  exactly as it would at home. That transparency is the property worth testing hardest.

### 2. `src/runtime/manifest/` — the YAML manifest

Per spec/09. Zod-validated, since zod is already a dependency on the server side — but note the
manifest is loaded by the **browser**, so do not pull zod into the browser bundle if the existing
codegen boundary (`spec/01`, "no zod, no mesh imports in the browser bundle") would be violated.
If validating in the browser genuinely requires zod, say so in your summary and explain the
trade-off rather than quietly importing it.

- `site` block, `layout` (regions and which roles each slot accepts), `apps` (id, module, load
  strategy, auth gating, surfaces), and the `remotes` block.
- Produces the `LayoutPolicy` the existing compositor already consumes. Do not redesign that shape.
- **Load strategies**: `eager` and lazy. An app whose manifest marks it as requiring auth is **not
  loaded at all** for an anonymous visitor — not hidden, not loaded (spec/02's closing section).
- **`remotes` requires, per entry: an explicit allowlist entry, a pinned version, and an SRI hash.**
  A remote without SRI must be a validation error, not a warning. Federation is a trust decision
  and the spec is explicit that these are mandatory.
- Environment overlays, per spec/09.

### 3. Wire them to the existing host

The router drives app activation through the existing `AppHost` (`loadApp`/`activateApp`/
`deactivateApp`). Do not build a second lifecycle.

## Tests — `test/router/` and `test/manifest/`, DOM ones with the docblock

At minimum:
  - a modified click (cmd/ctrl/middle/`target=_blank`) is NOT intercepted; a plain same-origin
    click is
  - route params are signals: navigating updates a bound value without re-mounting the view
  - a prefixed remote app resolves its own internal routes identically to when it is unprefixed —
    same app code, both mount points
  - back/forward restores scroll position
  - a manifest with a remote missing an SRI hash fails validation
  - an auth-gated app is not loaded at all for an anonymous visitor (assert it never loaded, not
    merely that it is not visible)
